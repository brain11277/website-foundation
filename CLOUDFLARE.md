# Cloudflare Deployment: New-Site Setup

The deployment half of the foundation. Pairs with `FOUNDATION.md` (the structural
contracts) and `templates/` (drop-in config). Assumes a static Astro build, but
the indexing, redirect and header notes apply to any static site on Cloudflare.

## Choosing a stack

Cloudflare has two ways to host a static site. Both serve from the edge, both
give you free TLS and a custom domain, and both read the same `_headers` and
`_redirects` files.

| | **Workers Assets** | **Pages** |
|---|---|---|
| Status | Where new features land | Supported, not where new work goes |
| Config | `wrangler.jsonc` in the repo | Dashboard settings |
| Static-only site | Yes, no Worker script needed | Yes |
| Adding server-side logic later | Add a `main` entry point | Migrate to Workers |
| Per-branch preview URLs | Workers Builds, or your own CI | Built in, `<branch>.<project>.pages.dev` |
| Custom 404 | Explicit, `not_found_handling` | Auto-detected from `404.html` |

**Default to Workers Assets for a new site.** Cloudflare's own guidance is that
if you are starting a new project you should use Workers instead of Pages, and
that new features and optimizations are focused there. For a purely static site
this costs nothing extra: point `assets.directory` at your build output and
deploy, with no Worker script at all.

**Pages is still a reasonable choice** if you want dashboard-managed Git
deploys and per-branch preview URLs without wiring up CI, and you are confident
the site will stay static. Path B below covers it.

Whichever you pick: static where possible, a Worker script only where dynamic
behavior is genuinely required.

# Stack-independent contracts

These three bite on both stacks. Get them right before worrying about which
host you are on.

## 1. One URL shape per URL (FOUNDATION §1, restated because it bites here)

Cloudflare's asset server redirects between slashed and unslashed forms. If your
build emits `/about/index.html` (Astro's `build.format: 'directory'`), the host
treats `/about/` as canonical and redirects `/about` to it. If your canonical
tags and sitemap emit `/about`, Googlebot fetches the submitted URL, gets a
redirect, and files **"Page with redirect"** on every page.

**Fix:** `trailingSlash: 'never'` plus `build.format: 'file'`, so pages build as
`/about.html` and serve at `/about` with no redirect. Config in
`templates/astro.config.mjs`.

The rule is that every layer agrees **for a given URL**, not that the whole site
uses one shape. A hand-authored directory under `public/` is a folder index and
correctly serves with a trailing slash, even on a site whose Astro routes are
slashless. What matters is that the sitemap lists the form the host returns a
`200` for. Do not "fix" a correct folder index into a redirect.

## 2. `_headers` rules are additive, not override

**A more specific path does not beat a broader one.** Every matching rule
contributes its headers, and a header set by two matching rules is joined with a
comma. This is documented behavior on both stacks and it is not what most people
assume.

A real incident: a broad prefix rule and a narrower font rule both set
`Cache-Control`, and the deployed header came back as

```
public, max-age=3600, stale-while-revalidate=86400, public, max-age=31536000, immutable
```

Malformed, with the first `max-age` winning regardless of which rule was more
specific.

**Write one flat rule per prefix.** If you want different caching for a subtree,
do not layer a second rule on top of a rule that already matches it.

```
# public/_headers: security baseline + cache policy
/*
  X-Frame-Options: DENY
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin

# Content-hashed build output only. A new build produces a new filename, so
# these are safe to freeze. Never put `immutable` on a path you overwrite.
/_astro/*
  Cache-Control: public, max-age=31536000, immutable
```

Note the `/*` block above sets no `Cache-Control`, deliberately. Adding one
there would concatenate with the `/_astro/*` rule for every hashed asset.

**`_headers` does not apply to responses generated by Worker code**, including
when `run_worker_first` is set. Set those headers in the script itself.

## 3. One canonical host

Pick apex (`example.com`) **or** `www`, and 301 the other to it. Mixed hosts
split your ranking signal and break the contract in FOUNDATION §1.

```
# public/_redirects
https://www.example.com/*  https://example.com/:splat  301
```

The same applies to microsites. Prefer serving them from a **path** on the main
domain (`example.com/tool`) over a subdomain, and 301 the subdomain inbound if
it already exists. A subdomain is a separate property: it needs its own
`robots.txt` and sitemap, and it builds its own entity graph instead of adding
to yours. Consolidating onto paths means one set of crawl signals, one schema
graph, and one thing to verify.

# Path A: Workers Assets (default)

## Configuration

Everything lives in `wrangler.jsonc` at the repo root. See
`templates/wrangler.jsonc`.

```jsonc
{
  "name": "example-site",
  "compatibility_date": "2026-01-01",
  "assets": {
    "directory": "./dist",
    // Pages auto-detected a 404.html. Workers does not: the default is "none",
    // so a styled 404 page will never render until you set this.
    "not_found_handling": "404-page"
  }
}
```

- **`not_found_handling` defaults to `"none"`.** This is the single easiest
  thing to get wrong when coming from Pages. The site builds, the 404 page ships
  in `dist/`, and unmatched URLs return an empty-bodied `404` forever. Set it to
  `"404-page"` for a static site, or `"single-page-application"` for an SPA, and
  then actually request a nonexistent path to confirm.
- **`html_handling` defaults to `auto-trailing-slash`**, which serves `foo.html`
  without a slash and `foo/index.html` with one. That is why `build.format:
  'file'` works here with no extra config. If you want the host to enforce it
  explicitly, set `"drop-trailing-slash"`.
- **`binding` is only valid alongside `main`.** An assets-only Worker should
  omit it; adding it without a script is a config error.
- **`.assetsignore`** in the assets directory replaces the exclusions Pages did
  automatically:
  ```
  **/node_modules
  **/.DS_Store
  **/.git
  ```

## When you need a Worker script

Add a `main` entry point and an `ASSETS` binding. The script handles what it
recognizes and falls through for everything else:

```js
return env.ASSETS.fetch(request);
```

Reach for a script for API proxying (an upstream that blocks browser CORS, or
one that 403s CI runner IPs but not edge IPs), scheduled jobs via
`triggers.crons`, inbound redirects that consolidate old hostnames onto paths,
or a KV-backed read cache. On the last one: read-then-merge, never replace
wholesale (FOUNDATION §5), so records do not roll off.

**`run_worker_first`** makes the script run before static-asset resolution. You
need it when the script must serve a path prefix whose routes collide with root
assets (`/`, `/favicon.svg`, `/robots.txt`). Everything else still falls through
to `env.ASSETS.fetch(request)`, so normal serving is unchanged.

Secrets go in `wrangler secret put <NAME>`, never in the config file. Note that
`wrangler.jsonc` is committed, so KV namespace IDs and any destination address
in it are public to anyone who can read the repo.

## Deploys and previews

`npx wrangler deploy`, or connect the repo through **Workers Builds** for
push-triggered deploys. Per-branch preview URLs are not automatic the way
`*.pages.dev` is, so either enable preview URLs on Workers Builds or run the
verification step in CI against the deployed URL.

# Path B: Pages

Still supported, and a fine choice for a site that will stay static and wants
zero-config Git deploys.

Cloudflare dashboard → **Workers & Pages → Create → Pages → Connect to Git**.

| Setting | Value |
|---|---|
| Framework preset | Astro (or *None* for a custom build) |
| Build command | `npm run build` |
| Build output directory | `dist` |
| Root directory | repo root (or the subdir if monorepo) |
| Node version | pin via `NODE_VERSION` env var (e.g. `20`) to match local |

- Production branch is `main`. Every other branch gets a preview deploy at
  `<branch>.<project>.pages.dev`. Run `verify-indexing.mjs` against these.
- Set environment variables in **both** Production *and* Preview. A var missing
  from Preview is the most common "works in prod, broken in preview" cause.
  Public, build-time vars are conventionally prefixed `PUBLIC_`.
- Pages detects `404.html` and serves it automatically, so the Workers
  `not_found_handling` gotcha does not apply here.

## Custom domain & DNS (both paths)

- Add the domain to the Worker or Pages project under **Custom domains**. If the
  domain's DNS is already on Cloudflare, records are added for you.
- Pick one canonical host and 301 the other, per contract §3 above.
- SSL/TLS → **Always Use HTTPS: On.** Add HSTS once HTTPS is solid.

---

## Deploy verification (don't trust green)

After the first production deploy and on every meaningful change:

```bash
node scripts/verify-indexing.mjs https://example.com
```

It fetches the sitemap, then every URL with redirects disabled, and fails on any
`3xx`, non-`200`, canonical mismatch, or unresolved JSON-LD `@id` reference,
catching the "Page with redirect" class before Search Console does. Wire it into
CI against whichever URL your stack gives you: a Pages preview deploy, a Workers
preview URL, or production immediately after deploy.

Two things the script cannot check for you:

- **Request a nonexistent path** and confirm you get your styled 404 page and a
  `404` status, not an empty body. On Workers Assets this is the
  `not_found_handling` default biting.
- **Open devtools on the live page** before asserting anything about analytics,
  cookies or tracking in your copy. Cloudflare Web Analytics is injected at the
  edge from a dashboard toggle and appears in no file in your repo, so a "no
  analytics, no tracking" claim can be false without anything in Git saying so.

## Launch checklist

Both stacks
- [ ] one canonical host chosen; the other 301s to it
- [ ] `_headers` security baseline in place, one flat rule per prefix
- [ ] no `immutable` on any path that gets overwritten in place
- [ ] custom domain live; Always Use HTTPS on
- [ ] Cloudflare Web Analytics enabled (and any privacy copy checked against the live page)
- [ ] `verify-indexing.mjs` green against the production domain
- [ ] a nonexistent path returns your styled 404 page, not an empty body
- [ ] any Worker script: secrets set via `wrangler secret put`, cron schedule confirmed

Workers Assets
- [ ] `assets.directory` points at the build output
- [ ] `not_found_handling` set explicitly
- [ ] `binding` present only if `main` is
- [ ] `.assetsignore` covers `node_modules`, `.DS_Store`, `.git`
- [ ] preview URLs available via Workers Builds, or CI verifies production

Pages
- [ ] build command `npm run build`, output `dist`
- [ ] `NODE_VERSION` pinned to match local
- [ ] env vars set in **both** Production and Preview
